A · Executive Summary

The app has strong engineering bones: a clean design system, consistent component patterns, hardened auth internals (scrypt hashing, expiring/secure sessions, login rate-limiting), 30 passing unit tests, paginated lists, a real PDF pipeline, an error boundary, a health check, and a solid responsive pass. As a demo, it presents well.

For a real client launch it is not ready, and the blockers are concentrated in security and trust:

The single biggest issue

The entire app is public. src/proxy.ts lets every request through, and getCurrentAgent() falls back to the first agent for anonymous visitors. So anyone with the URL can read and mutate all data — create/delete contacts, delete team users, clear the owners database, upload files, trigger bulk sends — acting as the demo agent. Everything else is secondary to this.

  • Broken demo assets. public/seed/ does not exist, so every /seed/*.jpg|.pdf|.ogg reference (document previews, voice notes, brochures) 404s. Leftover Next.js starter SVGs (next.svg, vercel.svg, …) remain in public/.
  • Real security gaps independent of the gate: an open redirect (/api/media/[id] 302s to a user-controlled URL), no file-upload size/type limits, no CSV import cap, destructive actions with no confirmation (delete user, delete media), the default password printed on the login screen, and a dev "Simulate inbound" button exposed in production.
  • No authorization model. Any logged-in user can delete other users; there are no roles (admin/staff). No password-reset or change-password flow exists.

Major strengths

Design consistency · auth crypto quality · unit-test coverage of pure logic · mobile responsiveness · graceful error/empty states · privacy/terms scaffolding.

Major weaknesses

Public access · broken assets · missing input hardening · no RBAC · no account recovery.

Overall UX

Competent and clean once inside, but undermined by broken images and an unmistakably "demo" feel (exposed password, simulate button, fake-but-real-looking PII).

B · Critical Issues

Each issue lists where it appears, why it matters, severity, the fix, and the expected impact after fixing.

1 App is fully public / no auth enforced Critical

Where
src/proxy.ts (pass-through middleware) + src/server/agent.ts (getCurrentAgent first-agent fallback).
Why it matters
Anyone with the URL reads and writes all data as the demo agent. Complete loss of confidentiality and integrity for a real tenant.
Fix
Re-enable the gate: restore the redirect-to-/login in proxy.ts. In server actions, resolve the agent from the session only (no first-agent fallback for browser requests) and throw/redirect if absent. Keep the webhook/script path as an explicit, separate code path.
After fixing
Data is private; only authenticated users can act.

2 Open redirect High

Where
src/app/api/media/[id]/route.ts → NextResponse.redirect(asset.externalUrl).
Why it matters
externalUrl is unvalidated user input (addMediaLink stores any string). An attacker creates a media "link", shares /api/media/<id>, and the victim is redirected anywhere — phishing/credential harvesting under your own domain.
Fix
Don't server-redirect to user URLs. Render external links client-side as plain anchors. If a redirect is required, allowlist https: plus known hosts (YouTube/Vimeo/Drive) and reject everything else.
After fixing
No open-redirect vector.

3 Broken seed assets (404s) High

Where
public/seed/ is missing; referenced throughout prisma/seed.ts (/seed/*.jpg/.pdf/.ogg).
Why it matters
Document previews, voice notes and brochures all 404. The product looks broken/unfinished to anyone evaluating it.
Fix
Either add real placeholder assets under public/seed/, or change the seed to omit file URLs and render a "no preview" state. Remove the leftover starter SVGs (next.svg, vercel.svg, globe.svg, window.svg, file.svg).
After fixing
Clean, professional demo with working previews.

4 No file-upload limits High

Where
src/server/media-actions.ts, src/server/document-actions.ts — only check instanceof File && size !== 0.
Why it matters
Any (anonymous) user can upload arbitrarily large or arbitrary-type files → storage abuse, denial of service, hosting cost.
Fix
Enforce a max size (e.g. 10 MB documents / 50 MB video) and a content-type allowlist server-side before writing to storage; reject with a clear error otherwise.
After fixing
Uploads are bounded and type-safe.

5 Default password shown on login High

Where
src/components/auth/login-form.tsx — renders Demo password: klientflo when APP_PASSWORD is unset.
Why it matters
If deployed without APP_PASSWORD, the working password is printed publicly and it's the well-known default. Instant account takeover the moment the gate is enabled.
Fix
Never render the actual password. Remove the hint in production (gate it behind a DEMO_MODE flag, or drop it entirely). Require a non-default APP_PASSWORD / seeded user in production.
After fixing
No credential disclosure.

6 Destructive actions without confirmation Medium

Where
team-settings.tsx (delete user) and media-manager.tsx (delete media) — plain <form action> submit, no prompt. (Template/owners deletes do confirm — inconsistent.)
Why it matters
One click permanently deletes a user or asset, with no undo and no prompt — easy accidental data loss and support tickets.
Fix
Add a confirmation step (a single consistent styled dialog, not native confirm() in some places and nothing in others) for all deletes. Ideally soft-delete users.
After fixing
Fewer accidental deletions; consistent behaviour.

7 Unbounded CSV import Medium

Where
src/server/owner-actions.ts → parseOwnerCsv then createMany.
Why it matters
No row/byte cap; a huge CSV blocks the request and bulk-inserts unbounded rows.
Fix
Cap input bytes and rows (e.g. 5 MB / 10k rows); chunk createMany; return a clear "file too large" message.
After fixing
Import is safe at scale.

8 Webhook accepts unsigned payloads when app secret is unset Medium

Where
src/server/whatsapp.ts — verifySignature returns true if WHATSAPP_APP_SECRET is missing.
Why it matters
In a half-configured production (WhatsApp token set, app secret missing), anyone can POST fake inbound messages → fake conversations, AI spend, auto-replies.
Fix
Fail closed: if WhatsApp is configured (isWhatsAppConfigured()), require a valid signature regardless; only skip verification in an explicit demo mode.
After fixing
No forged inbound messages.

9 "Simulate inbound" exposed in production Low / Med

Where
src/app/(app)/inbox/page.tsx → SimulateInboundButton.
Why it matters
A dev/demo affordance lets anyone inject fake messages in production.
Fix
Hide behind a DEMO_MODE / non-production flag.
After fixing
Cleaner production UI; no fake-data injection.

10 No password reset / change-password Medium

Where
No such flow exists anywhere.
Why it matters
Users can't recover or rotate credentials; admins must re-create accounts. Account-safety gap.
Fix
Add change-password (in Settings) and a token-based reset (email) before enabling the gate for real users.
After fixing
Self-service recovery; better account hygiene.

E · Accessibility Audit (WCAG-style)

Good already: global :focus-visible ring + prefers-reduced-motion; most icon buttons have title/aria-label; tables use semantic <thead>/<th>; client/property editors use real <label>s.

  • Inputs without programmatic labels — Team add-user (name/email/password), Owner search + import file input, bulk-send search, inbox/owner filter selects rely on placeholder only. Fix: add <label htmlFor> (visually hidden if needed) or aria-label on each.
  • Colour contrast (needs measurement) — text-foreground-muted on surface, and especially amber-700 on amber-500/10 (warning banners, 24h-window flag) are likely below 4.5:1. Fix: run axe/Lighthouse; darken muted text and the amber pair to meet AA.
  • Headings — some section titles are <p class="font-semibold"> not <h2>. Fix: use real heading levels.
  • Alt text — content images need meaningful alt; decorative icons should be aria-hidden. (Brand "K" and avatar initials are text — fine.)
  • Confirm dialogs — native confirm() is accessible but inconsistent; a styled dialog should be focus-trapped and labelled.
  • Error messages — form errors render as visible text but aren't wired to fields via aria-describedby/aria-invalid, nor in an aria-live region. Fix: associate & announce.
  • Touch targets — several icon buttons are p-1.5 (~28px), below the 44px guideline. Fix: bump to ~40–44px on touch.

Cannot fully verify from code: contrast ratios, screen-reader output, keyboard traps — these need a live run with axe-core + a screen reader.

F · Security, Privacy & Abuse-Prevention Review

Reviewed from a safe, non-destructive, product/QA/configuration perspective. No exploitation performed.

Authentication / login

Flow is clear; errors are generic (good — no user enumeration); login is rate-limited (10/5min/IP); passwords are scrypt-hashed; sessions are HMAC-signed with expiry + httpOnly + Secure(prod) + SameSite=lax. But the gate is off, the default password is displayed, there's no reset/change-password, and AUTH_SECRET falls back to a dev string if unset (mitigated — Render auto-generates it).

Authorization / roles

No authorization layer. With the gate open, anonymous = the first agent. Even with the gate on there are no roles — any user can delete other users (deleteTeamUser). Page separation doesn't exist beyond "logged in or not." Data queries are agent-scoped (good), but there's a single tenant. Fix: session-based agent resolution; add at least admin vs member roles for destructive ops.

Forms / input handling

Basic required-field checks; file uploads unrestricted (size/type); CSV unbounded; addMediaLink accepts any URL (feeds the open redirect). Fix: validate sizes/types/URLs; cap imports.

Sensitive data

Demo PII (names, phones, emails, owner records) is publicly exposed via the open gate. Passwords stored hashed (good). No payment data in scope. /api/health discloses DB up/down (minor). Fix: the gate fixes the big exposure.

Privacy / compliance

Good Privacy Policy + Terms exist (template, noindex), linked from login; robots noindex set. Gaps No cookie/consent banner; no in-product consent capture for WhatsApp messaging (PDPL + Meta opt-in). Fix: add consent capture for messaging and a cookie notice if analytics are added.

Payment / checkout

Not applicable — no payments in scope.

Trust & account safety

HTTPS via Render Good. Destructive actions inconsistently confirmed. No account-activity notifications; no email-change/password-change flows. Fix: add confirmations + notifications before real launch.

Error handling / information leakage

Good error.tsx logs server-side and shows a friendly message (no stack trace); friendly not-found; webhook returns terse statuses. No obvious DB/stack leakage to users.

Abuse prevention

Login + webhook rate-limited Good. No CAPTCHA / duplicate-submit guards on create/send actions; bulk send has no daily cap; simulate-inbound exposed. Fix: disable-on-submit, idempotency on sends, per-day send caps in real mode.

Security headers: no headers config found (CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy) — likely absent. Add them in next.config headers().

G · Conversion & User Journey Review

This is an internal operations tool, not a marketing funnel, so "conversion" = agent activation (getting a real agent messaging through it).

  • No onboarding / first-run guidance. A new agent lands on a dashboard with no "connect WhatsApp / import contacts / step 1". Fix: a setup checklist on the dashboard (Connect WhatsApp → Import owners → Tag your first conversation).
  • No value-proposition surface. The open root/login doesn't say what it does or why to trust it. Fix: a short value line + the (existing) privacy/terms links.
  • Demo vs real ambiguity. "Demo mode" chips exist in the inbox, but other sections look "live" while running on mocks. Fix: a consistent "Demo / not connected" banner tied to isWhatsAppConfigured()/isAIEnabled().
  • In-flow next-action clarity is good (suggested actions, AI suggestions) — keep it.

J · Performance & Perceived Speed

  • Every app page is force-dynamic → server-rendered per request, each hitting Postgres. First paint waits on the DB; the new loading.tsx skeleton helps perceived speed. Consider caching read-heavy, low-volatility pages.
  • Reports does a ranged message.findMany with no limit and aggregates in JS — fine now, slow at scale (already flagged in code). Move to a SQL rollup before large data.
  • Broken /seed/* assets cause failed requests + layout jank on any page that renders them.
  • No next/image usage found → real property photos (when rendered) won't be optimised/lazy-loaded. Add next/image.
  • PDF generation (@react-pdf renderToBuffer) is synchronous server work; large bulk sends add latency — fine for demo, watch under load.
  • Animations are light (pulse skeleton, transitions); reduced-motion respected. Good.
  • No real metrics (LCP/TTI/CLS) available without running Lighthouse against the live URL.

Reviewer's honest note

Most of the critical security findings stem from the access gate being open, which was a deliberate choice for the demo. That's completely fine for a demo link — but the moment a real client's data goes in, Issues 1–8 are non-negotiable. A practical approach: keep the demo experience behind a DEMO_MODE flag (so it can still be shown off openly), and make production secure-by-default.

What would deepen this audit

To turn the "likely" accessibility/performance/cross-browser findings into measured ones, the reviewer needs: the live Render URL; test credentials with the gate ON; permission to run Lighthouse + axe-core; real devices/browsers (Safari/Firefox/Edge — especially the Web Speech mic); and confirmation of the Render env vars actually set (to distinguish demo-mode from real-mode behaviour).
